# claude-code-session-handoff

Claude Code 会自动压缩长会话：它删掉你对话的大部分内容，用一段摘要取而代之，然后继续。
你通常是这样发现的——模型开始重新询问两小时前就已经定下来的事情。

这个仓库采取另一种做法。它测量会话真正的占用量，当终点确实临近时，把整个会话导出到磁盘，
然后在一个新会话中继续——而这个新会话在做任何事之前，会**完整读完父会话的记录**。
没有任何东西被摘要掉，会话之间的链路始终可见、可恢复。

它还诊断出一个值得了解的配置陷阱——即使你根本不打算安装本工具，也建议看一眼
[被钳制的窗口](#被钳制的窗口)。

## 安装

需要 Python 3.8+ 和 Claude Code。没有其他依赖需要安装。

```bash
git clone https://github.com/IRDcode/claude-code-session-handoff
cd claude-code-session-handoff
python install.py --dry-run     # 先查看所有将要发生的改动
python install.py
```

然后重启 Claude Code，看看它测出了什么：

```bash
python ~/.claude/skills/long-session-handoff/scripts/session_weight.py --explain
```

默认安装**不会**改变 Claude Code 管理上下文的方式。自动压缩保持原样；
这个守卫只是在压缩能够触发之前就完成交接。要全部移除：

```bash
python install.py --uninstall
```

`settings.json` 在被修改前会先备份，你已有的 hooks 和状态栏不会被动，重复安装是幂等的。

## 安装了什么

| 路径 | 内容 |
|---|---|
| `~/.claude/skills/long-session-handoff/` | 模型遵循的流程，以及三个脚本 |
| `~/.claude/hooks/session-weight-watch.py` | 检测器，注册在四个事件上 |
| `~/.claude/hooks/statusline-weight.py` | 每次渲染都在状态栏显示占用量 |
| `~/.claude/runtime/` | 防打扰状态、日志、测量缓存 |
| `~/.claude/handoffs/` | 导出内容，以及把父子会话连起来的 `chains.json` |

注册四个 hook 事件——`UserPromptSubmit`、`SessionStart`、`PreCompact`、`PostCompact`。
你在这些事件上已有的 hooks 会被保留。

## 与默认行为的区别

| | 默认的 Claude Code | 安装本工具后 |
|---|---|---|
| 会话满了的时候 | 自动压缩触发；大部分对话被丢弃并替换为摘要 | 在那之前很久，就会先向你提议交接 |
| 下一个会话知道什么 | 摘要捕捉到的内容——而写摘要的正是那个已经开始跟不上的 agent | 父会话自己的完整记录，并用计数校验读全了 |
| 被丢弃的历史 | 在当前会话中已无引用 | 从磁盘恢复到 `05-dropped-context.md` |
| 到底满了多少？ | `/context` 显示窗口占比 | 状态栏显示的是真正终结会话的那道墙的占比 |
| 事后怎么找到续接会话 | 翻 `/resume` | `chains.json` 记录了父、子、迁移时的占用量，以及读取是否已校验 |

状态栏长这样：

```
Opus 5 | ████████░░ 85% 830k/977k | 696t 402tc 6.1h | HANDOFF DUE (5) | no-compact
```

是**墙**的百分比，不是窗口的百分比。两者不同，有时相差五倍——这正是下一节的全部要点。

## 被钳制的窗口

即使你什么都不安装，这一节也值得读。

Claude Code 有两个不同的会话终点：

```
压缩触发于    窗口   − 回复预留(~20k) − 摘要缓冲(~13k)
拒绝发送于    上限   − 回复预留(~20k) − 余量(~3k)
```

自动压缩开启时是第一个，关闭时是第二个。所以一个 200,000 的窗口大约在 **167,000** 处压缩。

陷阱在这里：**`settings.json` 里的 `autoCompactWindow` 会被静默钳制到模型上限。**
在 200,000 的上限下请求 1,000,000，你得到的是 200,000——而界面上没有任何地方提示这一点。
一个按一百万 token 配置的会话，会在 167,000 处被压缩，连续三次，
同时约 830,000 个你已付费的 token 完全没被用到。

这不是假设。它就是本仓库的由来：三次压缩，`preTokens` 分别是
**167,398 / 167,071 / 166,904**，而配置文件里写着 `autoCompactWindow: 1000000`。

`--explain` 会告诉你自己属于哪种情况：

```
WINDOW
  client reported  1,000,000
  ceiling          1,000,000   (source DISABLE_COMPACT+CLAUDE_CODE_MAX_CONTEXT_TOKENS)
  resolved         1,000,000   (source settings)

WALL -- the token count past which no more work happens here
  1,000,000 ceiling - 20,000 reply reserve - 3,000 margin
  = 977,000   then SENDING IS REFUSED (no summary; a handoff is the only exit)
```

如果它显示 `settings CLAMPED to …`，说明你的窗口设置正在被压低。

只有一种配置能绕过钳制：`DISABLE_COMPACT=1` 搭配 `CLAUDE_CODE_MAX_CONTEXT_TOKENS`。
安装器可以帮你设置，但它会先询问并告知代价，因为**这同时也会禁用手动 `/compact`**：

```bash
python install.py --disable-compact --window 1000000
```

设置之后，会话不再以摘要收尾——而是以拒绝发送收尾。这是一个真实的权衡。
拒绝发送是可以承受的：你交接，然后继续。被静默销毁的历史则不可承受。
但如果你一路忽略所有提示直到撞墙，那个会话就不再接受新的轮次了，这一点你应当事先知道。
守卫在 85% 触发，留出约 147,000 token 的余地，所以实践中不会走到那一步。

如果你更想保留 `/compact`，跳过这个开关。交接功能照样能用。

## 兼容性

这里没有任何代码去修补或包装 Claude Code。它只读两个有文档的接口——hook 的
stdin/stdout 约定和状态栏载荷——并解析客户端本来就会写的 JSONL 记录。
这就是它能扛过那些会让"依赖内部实现"的工具崩掉的更新的原因。

需要确切数字时，取自证据而非断言，共三层：

1. 窗口来自 `context_window_size`——客户端每次渲染状态栏时自报的值。
2. 若该会话曾被压缩，触发点取自记录中当时的 `preTokens`——这是被观测到的触发点，
   不是算出来的。`score()` 优先采用它，并在采用时标注
   `corrected from observed preTokens`。
3. 两者都没有时，才退回到预留算术；`--explain` 会列出每个输入，让偏移可见而非沉默。

**较旧的 Claude Code 版本。** 四个 hook 事件和状态栏已经稳定了很多个版本。
若你的版本缺少某个事件，那个 hook 就不会触发，其余照常工作——检测器是叠加的，不是替换。
`--disable-compact` 是唯一依赖具体设置名的部分；如果它没生效，`--explain` 会告诉你。

**操作系统。** 纯 Python，无依赖，无编译组件。路径一律走 `os.path`，
到处都尊重 `CLAUDE_CONFIG_DIR`，安装器会挑一个在*你的* shell 里真正可用的解释器名，
而不是硬编码。唯一涉及平台的代码是强制 stdout 用 UTF-8——Windows 需要，别处无害。

在你自己的机器上验证：

```bash
python tests/test_session_weight.py    # 算术、闸门、两个陷阱
python tests/test_compat.py            # 语法下限、入口点、hook 输出
```

`test_compat.py` 会找出你机器上其他所有 Python 并在每一个下重跑套件，
于是版本差异会表现为一次失败，而不是日后的意外。

## 什么时候触发

测量七个信号。**是否**迁移只由上下文决定；其余信号只影响**有多急**。

| 信号 | 阈值 |
|---|---|
| 上下文 vs 墙 | ≥ 85% → 交接，≥ 95% → 不再询问，直接执行 |
| assistant 轮次 | ≥ 900 |
| 工具调用 | ≥ 600 |
| 活跃工作时间 | ≥ 4 小时 |
| 自动压缩已经发生过 | 任意次 |

**低于墙的 62% 时，无论其他信号如何，都不会提议交接。**
这道闸门存在的原因是：其余信号都是上下文压力的*替代指标*，
诞生于无法直接测量上下文的年代。用构建本工具的那个会话实测：
4.3 小时工作加上两次先前的压缩，评分已达"立即交接"，而上下文只在 977,000 中的 147,527——15%。
那时迁移会白扔 829,473 个 token，什么也换不回来。

两个看起来不起眼但很关键的测量细节：

- **活跃时间是所有小于 10 分钟的间隔之和**，而不是末减初。一个开着过夜的会话
  跨度读作 44 小时、实际工作 11 小时；按跨度计分会在一个空闲会话上触发交接。
- **压缩次数从记录中的类型化行读取**，绝不用搜索标记字符串的方式。
  你搜一次那个标记，它就出现在你自己的工具输出里，计数于是自我膨胀。

提示每档最多出现一次——再 200 轮，或者再跨过墙的十分之一——且有 15 分钟下限。
在子 agent 内部永不触发。

## 交接过程

```
测量  →  询问  →  导出  →  创建续接会话  →  它读完父会话
```

导出会写五个文件：逐字保留的每一条用户消息（包括轮次中途发出的那些，很容易丢），
每一条实质性的 assistant 消息，工具载荷已裁剪的完整记录，一份计数索引，
以及之前压缩丢掉的内容。

随后续接会话被创建，并在你打开它之前就被**无头唤醒**去读这些导出。
它必须回复与索引相符的计数——若不相符，说明只读了一部分，交接尚未完成。
这次阅读发生在没人等待的会话里，所以迁移中最耗时的部分不占用你的等待时间。

之后你会拿到 id 和名字：

```
claude --resume 7157caa1-11ce-4f29-a46a-09913d483fb0
```

或者在 `/resume` 里搜名字——名字带着父会话的主题词加上 `(cont. 2)`。

## 自己验证

上面每一项说法都能在你自己的机器上核对。脚本输出的是数字，不是安慰：

```bash
# 我的会话到底在哪里结束，为什么？
session_weight.py --explain

# 当前占用量是多少，每个信号都列出来
session_weight.py --session-id <uuid>

# 机器可读
session_weight.py --session-id <uuid> --json
```

要确认某个配置改动是否生效，不要信文件——读记录。
找到第一个 token 总数越过旧触发点的轮次，检查它之后没有新的压缩行。

## 局限

坦白说明，因为一个用来测量的工具应当诚实交代自己没测过什么：

- 各项预留（~20k / ~13k / ~3k）来自观察到的行为。未来的版本可能改动它们。
  防线有三层：客户端自报的窗口、记录中真实的 `preTokens`（即被观测到的触发点，
  `score()` 会优先采用它），最后才是这套预留算术——只有第三层是推测。
- 拒绝发送那道墙是计算并交叉验证出来的，没有刻意去撞。守卫的设计就是让你到不了那里。
- 在 Windows 上以 Python 3.11、3.12、3.14 测试过，并针对 3.8 语法做了检查。
  Linux 与 macOS 应该没问题——除控制台编码外没有平台相关代码——但都未做端到端运行。
- 五文件导出与评分器由测试套件覆盖。无头唤醒那一步取决于你的 `claude` 可执行文件能否被启动；
  若不能，导出照样成功，工具会告诉你接下来怎么做。
- 提示缓存：交接会开启新会话，因此缓存是冷的。对一个已经接近墙的会话这是划算的交换，
  但它仍然是一项成本。
